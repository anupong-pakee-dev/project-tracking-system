## 1. ภาพรวมโปรเจค

### 1.1 วัตถุประสงค์
ผู้ใช้ทำโปรเจคหลายตัวพร้อมกัน (ปัจจุบัน 3 ตัว) และต้องการ
1. อัปเดตความคืบหน้าของแต่ละโปรเจคได้เร็ว
2. รู้ว่า **โดยประมาณจะเสร็จวันไหน**
3. รู้ว่า **คลาดเคลื่อนจากแผนแค่ไหน** — ทันเป้าหรือไม่ ช้ากี่วัน ต้องเร่งเท่าไร
4. เห็นภาพรวมทุกโปรเจคในหน้าเดียว เพื่อตัดสินใจว่าควรโฟกัสโปรเจคไหน

### 1.2 ผู้ใช้เป้าหมาย
- นักพัฒนา / ฟรีแลนซ์ที่ทำหลายโปรเจคพร้อมกัน — แต่ละคนมีบัญชีและข้อมูลแยกกัน

### 1.3 เป้าหมายที่วัดผลได้
- อัปเดตความคืบหน้า 1 โปรเจคเสร็จภายใน 15 วินาที (เปิดหน้า → ปรับ → บันทึก)
- หน้าแรกบอกสถานะทุกโปรเจค (ตามแผน / เสี่ยง / ล่าช้า) ได้โดยไม่ต้องคลิกเพิ่ม
- วันคาดว่าเสร็จอัปเดตทันทีหลังบันทึก
- Unit test ครอบคลุม logic การคาดการณ์ทุกสถานะ

## 2. ขอบเขตของระบบ

**อยู่ในขอบเขต (In Scope)**
- สร้าง / แก้ไข / พัก / ปิด / ลบโปรเจค พร้อมวันเริ่มและวันเป้าหมาย
- แตกงานย่อย (task) พร้อม "ขนาดงาน" เพื่อถ่วงน้ำหนักความคืบหน้า
- บันทึกความคืบหน้าเป็นระยะพร้อมโน้ต (เก็บเป็นประวัติ)
- คาดการณ์วันเสร็จ + ช่วงความไม่แน่นอน + สถานะสุขภาพโปรเจค
- แดชบอร์ดรวม ไทม์ไลน์ และกราฟ burn-up รายโปรเจค
- สำรอง / กู้คืนข้อมูลเป็นไฟล์ JSON, ข้อมูลตัวอย่าง
- Dark mode ตามระบบ, ใช้งานบนมือถือได้

**นอกขอบเขต (Out of Scope)**
- ทีม / การแชร์โปรเจคระหว่างบัญชี
- เข้าสู่ระบบด้วย Google / OAuth, 2FA
- วันหยุดนักขัตฤกษ์ (รองรับเฉพาะการไม่นับเสาร์–อาทิตย์)
- การแจ้งเตือนผ่านอีเมล / LINE
- Dependency ระหว่างงาน, critical path แบบ Gantt เต็มรูปแบบ

## 3. สถาปัตยกรรมและ Tech Stack

```
Browser ──▶ apps/web (Next.js, :3000) ──HTTP/JSON + Bearer token──▶ apps/api (Fastify, :4000) ──Prisma──▶ PostgreSQL
                 └────────── packages/shared (types, วันที่, สูตรคาดการณ์) ──────────┘
```

- Browser คุยกับ **web** เท่านั้น — Server Actions / Route Handler ของ web เรียก API จากฝั่ง server
- **api** เป็นเจ้าของ business logic ทั้งหมด (ตรวจข้อมูล, บันทึกขอบเขตเปลี่ยน, ปิดโปรเจคอัตโนมัติ, คำนวณคาดการณ์) และทำงานใน transaction
- สูตรคาดการณ์อยู่ใน **shared** เป็น pure function — test ได้โดยไม่ต้องมีฐานข้อมูล

| ส่วน | เทคโนโลยี | เหตุผล |
|---|---|---|
| Frontend | Next.js 16 (App Router) + TypeScript strict | Server Components เรนเดอร์จากข้อมูล API, Server Actions สำหรับฟอร์ม |
| UI | Tailwind CSS v4 + CSS variables, ฟอนต์ Anuphan | Dark mode ด้วย token ชุดเดียว, อ่านง่ายทั้งไทย/อังกฤษ |
| กราฟ | SVG เขียนเอง (Server Component) | ไม่มี JS กราฟฝั่ง client |
| Backend | Fastify 5 (Node.js 24, TypeScript, รันด้วย tsx) | เร็ว, เบา, error handling ชัดเจน |
| Validation | Zod 4 | ตรวจทุก request + ไฟล์สำรอง, ข้อความ error ภาษาไทย |
| ORM | Prisma 7 + `@prisma/adapter-pg` | Type-safe, migration, รองรับ connection pooler |
| ฐานข้อมูล | PostgreSQL 17 — Docker (docker-compose) ตอนพัฒนา, Supabase / Neon เมื่อขึ้น cloud | Relational, foreign key + cascade; dev/test แยกฐานข้อมูลกัน |
| Testing | Vitest | Unit test สูตรคาดการณ์ + integration test API กับ Postgres จริง |
| Monorepo | npm workspaces + concurrently | `npm run dev` รันทั้ง web และ api |

## 5. อัลกอริทึมการคาดการณ์

นิยาม (ความคืบหน้าเป็น %; หน่วยวันคือ **วันปฏิทิน** หรือ **วันทำงาน จ–ศ** ถ้าโปรเจคเลือกไม่นับเสาร์–อาทิตย์ — ทุกช่วงเวลา, ความเร็ว, ความคลาดเคลื่อน และค่าที่ยอมได้ใช้หน่วยเดียวกัน):

| ค่า | สูตร |
|---|---|
| ความคืบหน้า `P` | Σ(ขนาดงาน × %งาน) ÷ Σ ขนาดงาน |
| แผนวันนี้ `Plan` | (วันนี้ − วันเริ่ม) ÷ (เป้าหมาย − วันเริ่ม) × 100 |
| ความเร็วรวม `Vall` | P ÷ (วันนี้ − วันเริ่ม) |
| ความเร็วล่าสุด `V14` | (P − P ณ 14 วันปฏิทินก่อน) ÷ จำนวนวัน (หรือวันทำงาน) ในช่วงนั้น (ใช้เมื่อโปรเจคเดินมาเกิน 14 วัน, interpolate จากประวัติ) |
| ความเร็วที่ใช้ `V` | 0.5 × V14 + 0.5 × Vall (ถ้ายังไม่มี V14 ใช้ Vall) |
| วันคาดว่าเสร็จ | วันนี้ + ⌈(100 − P) ÷ V⌉ วัน (หรือวันทำงาน — ข้ามเสาร์–อาทิตย์) |
| ช่วงเร็วสุด / ช้าสุด | ใช้ max/min ของ {V, Vall, V14, V×1.2, V×0.8} — ถ้าช้าสุด ≤ 0 แสดง "ไม่แน่นอน" |
| ความคลาดเคลื่อน | วันคาดว่าเสร็จ − วันเป้าหมาย |
| ค่าที่ยอมได้ | max(3 วัน, 10% ของระยะเวลาโปรเจค) |

**เหตุผลที่ผสมสองความเร็ว:** ความเร็วรวมนิ่งแต่ตอบสนองช้า ความเร็ว 14 วันล่าสุดตอบสนองไวต่อการช้าลง/เร่งขึ้น การผสมครึ่งต่อครึ่งทำให้วันเสร็จขยับเมื่อพฤติกรรมเปลี่ยนจริง โดยไม่แกว่งจากการอัปเดตครั้งเดียว

**จุดข้อมูลวันนี้:** ประวัติถูกต่อด้วยจุด (วันนี้, P) เสมอ — ถ้าไม่ได้อัปเดตนาน ความเร็วล่าสุดจะลดลงเอง ซึ่งสะท้อนความจริงว่างานไม่เดิน

**ลำดับการตัดสินสถานะ:** เสร็จแล้ว → พักไว้ → ยังไม่เริ่ม → เลยเป้าหมายแล้ว = ล่าช้า → ไม่มีข้อมูล → ความเร็ว 0 = ล่าช้า → slip ≤ 0 = ตามแผน → slip ≤ ค่าที่ยอมได้ = เสี่ยงล่าช้า → อื่นๆ = ล่าช้า

## 7. โครงสร้างข้อมูล (Database Schema — PostgreSQL)

| ตาราง | คอลัมน์หลัก |
|---|---|
| `users` | id UUID PK, email UNIQUE (ตัวเล็ก), password_hash (scrypt), email_verified_at NULL, created_at, updated_at |
| `sessions` | id, user_id → users (CASCADE), token_hash UNIQUE, expires_at, last_used_at, user_agent |
| `auth_tokens` | id, user_id → users (CASCADE), type ENUM(verify_email, reset_password), token_hash UNIQUE, expires_at, used_at NULL |
| `projects` | id UUID PK, user_id → users (CASCADE, NULL = ก่อนมีบัญชี), name VARCHAR(120), description, color, start_date DATE, target_date DATE, status ENUM(active, paused, done), skip_weekends BOOL, manual_progress FLOAT, completed_at DATE NULL, created_at, updated_at |
| `tasks` | id UUID PK, project_id → projects (CASCADE), title VARCHAR(200), weight FLOAT, progress INT 0–100, sort_order INT · index (project_id, sort_order) |
| `progress_logs` | id UUID PK, project_id → projects (CASCADE), date DATE, progress FLOAT (snapshot % รวม), note, kind ENUM(update, scope), created_at · index (project_id, date) |

วันที่ตามปฏิทินเก็บเป็น `DATE` และส่งผ่าน API เป็น `YYYY-MM-DD` · web ส่ง header `X-Client-Date` ให้ API ใช้ "วันนี้" ตรงกัน (ถ้าต่างจากเวลาเซิร์ฟเวอร์เกิน 1 วันจะใช้เวลาเซิร์ฟเวอร์) · schema อยู่ที่ `apps/api/prisma/schema.prisma`
## 8. หน้าจอหลัก (Screens)

| หน้า | Route | รายละเอียด |
|---|---|---|
| ภาพรวม | `/` | การ์ดสรุปสถานะ, ไทม์ไลน์, การ์ดโปรเจค, คำอธิบายวิธีคำนวณ |
| โปรเจค | `/projects/[id]` | สถิติ 4 ช่อง, ข้อความสรุป + คำแนะนำ, กราฟ burn-up, ฟอร์มอัปเดต, จัดการงานย่อย, ประวัติ |
| สร้างโปรเจค | `/projects/new` | ฟอร์มพร้อมแตกงานย่อยทันที |
| แก้ไขโปรเจค | `/projects/[id]/edit` | ฟอร์มแก้ไข |
| จัดการข้อมูล | `/data` | สำรอง, กู้คืน, ข้อมูลตัวอย่าง, ลบทั้งหมด (เฉพาะข้อมูลของบัญชีนี้) |
| เข้าสู่ระบบ | `/login` | อีเมล + รหัสผ่าน, ลิงก์ลืมรหัสผ่าน, ปุ่มส่งลิงก์ยืนยันอีกครั้งเมื่อยังไม่ยืนยันอีเมล |
| สมัครสมาชิก | `/register` | อีเมล, รหัสผ่าน, ยืนยันรหัสผ่าน |
| ตรวจอีเมล | `/check-email` | แจ้งให้เปิดอีเมล + ปุ่มส่งอีกครั้ง (โหมดพัฒนาแสดงลิงก์ Mailpit) |
| ยืนยันอีเมล | `/verify-email?token=` | ปุ่มยืนยัน → เข้าสู่ระบบอัตโนมัติ |
| ลืมรหัสผ่าน | `/forgot-password` | กรอกอีเมลเพื่อรับลิงก์ |
| ตั้งรหัสผ่านใหม่ | `/reset-password?token=` | รหัสผ่านใหม่ + ยืนยัน → เข้าสู่ระบบอัตโนมัติ |

หน้าที่ต้องเข้าสู่ระบบ: `proxy.ts` ส่งผู้ที่ไม่มี cookie ไป `/login?next=…` และหาก session หมดอายุ API ตอบ 401 → ไป `/login?expired=1`

## 9. REST API (apps/api)

ทุก endpoint ยกเว้น `/health` ต้องมี Bearer token (ถ้าตั้ง `API_TOKEN`) และ endpoint ข้อมูลต้องมี `X-Session-Token` ของผู้ใช้ · error ทุกตัวตอบ `{ "error": "<ข้อความภาษาไทย>" }` พร้อม status 400 / 401 / 404 / 500

| Method | Endpoint | หน้าที่ |
|---|---|---|
| GET | `/health` | สถานะ API + ฐานข้อมูล |
| POST | `/auth/register`, `/auth/login`, `/auth/logout` | สมัคร / เข้าสู่ระบบ / ออกจากระบบ |
| POST | `/auth/verify-email`, `/auth/resend-verification` | ยืนยันอีเมล / ส่งลิงก์อีกครั้ง |
| POST | `/auth/forgot-password`, `/auth/reset-password` | ลืมรหัสผ่าน / ตั้งรหัสผ่านใหม่ |
| GET | `/auth/me` | ผู้ใช้ปัจจุบัน |
| GET / POST | `/projects` | รายการโปรเจคพร้อมคาดการณ์ / สร้างโปรเจค (+ งานย่อย) |
| GET / PATCH / DELETE | `/projects/:id` | ดู / แก้ไข / ลบ (cascade) |
| PUT | `/projects/:id/status` | เปลี่ยนสถานะ |
| POST | `/projects/:id/tasks` | เพิ่มงาน |
| PATCH / DELETE | `/tasks/:id` | แก้ไข / ลบงาน |
| POST | `/tasks/:id/move` | เรียงลำดับ |
| POST | `/projects/:id/progress` | บันทึกความคืบหน้า |
| DELETE | `/logs/:id` | ลบประวัติ |
| GET / PUT | `/backup` | ส่งออก / กู้คืนทั้งหมด |
| POST | `/sample` | โหลดข้อมูลตัวอย่าง |
| DELETE | `/data` | ลบข้อมูลทั้งหมด |
| GET | `/stats` | จำนวนข้อมูล |

ฝั่ง web: `lib/api.ts` (HTTP client ฝั่ง server) · `lib/actions.ts` (Server Actions แปลงฟอร์มเป็น JSON) · `GET /api/export` (proxy ไฟล์สำรองให้ดาวน์โหลด)
